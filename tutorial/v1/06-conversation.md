# 补篇：让一个任务接着另一个任务

> 后续专题：本章描述已移出 v1 的交互实验。可用 `git switch -c my-chat-exercise 9c5cb11` 查看当时的可运行实现；当前 milestone/v1 已收敛为单任务核心，日常交互在 main。
读完前五章，我们已经有了一个能够读取、修改和验证文件的小 agent。它却还有一个日常使用时很容易察觉的问题：每执行一次任务，进程就退出。想接着问“刚才为什么这样改”，又得重新启动，并把前面的背景重新说一遍。

这一篇从 `step-05-v1` 的最小循环继续。我们给它补上最基本的终端交互，当时的实现保存在提交 `9c5cb11`。原来的小循环仍然可以单独阅读；新增代码负责输入、展示，以及让历史多活一会儿。本篇不加入 v2 的摘要、journal 或上下文投影。

## 先让程序等我们开口

在仓库启动目录的 `.env` 配置 `DEEPSEEK_API_KEY`，然后运行 `cargo run`。这是会访问真实模型的手动练习；下面的对话是预期操作，不是某次模型输出的转录。

```text
crab> 创建 note.txt，写入三种适合周末做的早餐。
crab> 把刚才第二种换成一道素食早餐，再读回来检查。
crab> /exit
```

第二句话里的“刚才”依赖前面的历史。即使模型重新读取了文件，知道为什么有这个文件、用户提出过什么要求，仍然有助于它正确继续。先不要急着做记忆数据库：同一个进程里的一个 `Vec<Value>` 就能表达这里需要的状态。

`src/cli.rs` 先决定启动方式。没有任务参数而且 stdin 是终端时，进入聊天；`-p "任务"` 执行一次；普通管道输入整体作为一次任务。需要用脚本按行演示聊天时，可以显式传 `--chat`。两种入口最后都调用同一个 loop，四个工具和模型协议没有分叉。

## 两层循环，各自等待不同的人

`src/terminal.rs` 的外层循环用 rustyline 读取输入。读到一条任务，便调用 `session.turn(task, progress)`；回答结束后，继续等待下一条输入。rustyline 已经处理了光标编辑和方向键历史，我们不用从终端控制序列开始写起。

`src/lib.rs` 里的内层循环仍然做熟悉的事：发请求、验证响应、执行工具、回传结果。不同的是，它用到的 `client`、工具声明和 `input` 现在放进 `Session`，不会在一个用户回合结束后被丢弃。新任务开始时，先向 `input` 追加一条 user message。模型返回的 output 也先保存，再判断是否结束，所以最终回答会留给下一次提问。

没有工具时，第二次请求的历史可以直接读成下面的顺序：

```text
user:      记住暗号 COBALT
assistant: 暗号是 COBALT。
user:      刚才的暗号是什么？
```

有工具的回合会多出 `function_call` 和对应的 `function_call_output`。不要只保存最后一段回答：工具反馈也是模型当时作出决定的依据。`call_id` 的关联规则与前几章相同，每组调用和结果按原次序保留。

现在运行 `cargo test --locked --test conversation`。测试使用本机 fake Responses 服务，检查第二个 HTTP 请求实际携带的历史；它证明客户端发送顺序正确，并不证明某个真实模型一定能回忆事实。`tests/cli.rs` 则启动真正的二进制，验证 `-p`、管道、多轮聊天以及指定工作区里的实际文件写入。

## 让进度可以被看见

用户输入任务之后，不应该只能等着屏幕毫无变化。loop 在请求模型前、调用工具前和工具返回后发出三个小事件：`Progress::Model`、`ToolStart`、`ToolResult`。聊天界面把它们显示成简短进度；单次任务入口沿用便于脚本读取的 stderr 工具记录。它们只是同一次执行的两种展示方式。

`/new` 丢弃当前 `Session`，下一条任务再创建新的历史。它保留磁盘上的文件，因此不要把“新对话”理解成撤销修改。退出也会丢弃内存历史；会话保存与恢复留给后面的版本。

Ctrl-C 发生在等待输入时，清掉当前输入；发生在执行回合时，取消这个回合，并将 `Session` 标为不能继续使用。HTTP 或协议错误也采用这个状态。原因很具体：一个写文件动作可能已经完成，而我们还没有拿到完整反馈。此时自动重发工具既不能恢复事实，还可能重复副作用。先检查文件，再显式 `/new`。普通工具错误仍按原来的方式回传模型，让它读取错误并修正参数。

## 再次碰到熟悉的预算

把历史保留得更久之后，请求自然会变大。这个历史交互实验保留完整历史，默认用 131,072 字节限制序列化后的请求；`CRABLOOP_CONTEXT_BYTES` 可以调整这个上限。达到预算时明确停止，界面可以 `/new` 开始新对话。这里没有偷偷截掉早期工具记录，也没有把字节数当作精确 token 数。

当时的交互实现是 571 行代码、581 物理行，统计覆盖所有 `src/**/*.rs`。与原来 314 行的 v1 相比，额外代码主要来自可用的 CLI、终端输入与会话边界。先读完那个小闭环，再逐步加上这里的交互，更容易区分模型行动、用户输入和状态寿命各自负责什么。后续 v2 的问题也随之清楚了：怎样在预算之内继续使用一段更长的历史？
