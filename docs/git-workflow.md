## main 重整建议（待确认后执行）

目标是让新的 v2 从同一份 v1 自然生长，而不是同时维护提前扩展的实现。main 源码本轮尚未重整，下面是建议的迁移方式。

先以 v1 GA 建立一次明确的基线整理提交：运行代码、依赖和教学增量对齐 v1，保留 main 的品牌资源、CI 与 roadmap，同时保留旧 main 的全部历史。推荐让该提交第一父节点为 v1 GA，第二父节点为旧 main：旧 main 仍是祖先，main 可以 fast-forward 更新；first-parent 的学习路线从 v1 继续，无需 force-push。

随后按下面的顺序演进，每批都提交可运行代码、实验和对应解释：

1. **Context state。** 先整理历史的所有权与执行记录；检查发送给模型的 input 及行为保持一致。
2. **Context projection。** 将执行记录和本次模型输入分开，保留当前任务、固定指令与完整 call/result 组，继续使用字节预算。
3. **Compaction。** 生成摘要候选，验证后才替换当前输入；失败时保留原历史，不增加自动重试或复杂恢复。
4. **任务与教学验收。** 在小预算下运行修复、资料整理和追问，检查约束与事实没有丢失，再补齐可复现教程。

旧 v2 标签用于参考机制，迁移时沿用新 v1 的接口与四工具，不整包恢复旧 CLI、展示和无关抽象。SSE、个人配置、provider presets、model catalog 等继续按后续版本安排。

只有当 main 上的 v2 实现与教程验收满意后，才创建新的 milestone/v2 学习分支。历史 v2 标签不移动，也不作为新路线已经完成的证明。

## 提交与保留

每批完成相关检查后提交并推送。历史教学提交和标签保留；发布阶段的学习分支不混入下一阶段能力。删除临时分支前确认其提交已被保留，处理工作区改动后再清理 worktree。
