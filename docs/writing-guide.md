# CrabLoop 教程写作约定

## 这份教程要陪读者完成什么

从一个空 Cargo 工程开始，亲手写出一个最小 coding-agent harness，再沿着运行中遇到的问题，逐步补上上下文管理与压缩。

读者可以有 Rust 基础，尚不需要理解 agent 框架。“从零”指完整展示 harness 怎样建立起来：第一条模型请求如何发出，一个工具调用怎样落到真实文件上，执行结果怎样进入下一轮，历史又怎样在多轮之后被整理。

叙述的目标是让读者一直知道：目前手里的程序能做什么，这一次为什么要修改它，改完之后该观察什么。

## 文笔与节奏

用耐心、清楚、连贯的中文，像坐在读者身边一起写程序。可以自然地使用“我们”，邀请读者先运行、观察或作出一个小判断。

语言简练，抓住主要信息。删去重复说明、泛泛表态和与当前主题无关的细节；roadmap 聚焦各版目标与范围，开发取舍和验收细节放在专门文档。

行业名称和技术术语尽量保留英文，例如 Harness、coding agent、context、compaction、provider、tool calling、session。需要时用中文解释含义，不另造带翻译腔的中文名称。CrabLoop 的目标是构建 mini coding agent 的 Harness；不要用 Workbench 或“工作台”扩大项目定位。

每段推进一个问题。相邻段落之间交代因果：一次观察为什么引出这个疑问，这个疑问为什么需要一段新代码。术语在第一次有用时介绍，解释后立即回到具体程序。

章节开头从上一章留下的程序状态或一个具体任务出发。结尾回到运行结果，让下一章的问题自然浮现。段落长短随内容变化，标题用来帮助定位真正的转折。

保持具体。尽量写“这次模型返回了文件路径和工具名”“程序把退出码放进下一次请求”，让读者能对应到数据和动作。技术选择注明其在当前学习阶段的理由。

## 代码怎样出现

先说明这段代码要解决的问题，再指出修改哪个文件、增添哪个函数或分支。每次代码增量围绕一个可以解释清楚的变化，给读者保留动手和观察的空间。

代码之后讲清数据从哪里来、交给谁、改变了什么状态。Rust 的所有权、借用、Result 或 async 在真正影响当前写法时展开；基础语法需要补充时，用短旁注或延伸阅读承接。

读者应能从每个节点继续运行：给出工作目录、命令、必要环境和预期现象，标明片段应当插入或替换的位置。章节关联对应 commit；阶段完整代码由 v1/v2 tag 保存。

展示完整文件适合放在阶段收束处。核心源码保持正常可读的格式，300/500 行是控制项目范围的目标。

## 运行、失败与证据怎样进入故事

让读者先观察一个正常结果，再改变一个条件，例如文件不存在、old_text 有两个匹配、测试返回非零退出码。解释这个变化暴露了程序的哪一个假设，然后只补上当前需要的机制。

给“预期输出”“示意交互”和“本次实测结果”明确的身份。真正的终端输出来自记录；没有运行过的例子标为预期或示意。模型响应可能不同，验收关注协议关系、文件状态和测试结果等可核对的事实。

工具失败后，沿着数据追踪：错误怎样返回、下一轮模型看到了什么、动作为什么改变。讲上下文压缩时，还要检查早期事实有没有丢失，而不仅仅展示输入变短。

## 每章需要照顾到的内容

写完后检查这些问题，不要求把它们逐个变成标题：

- 读者是否知道当前起点、这一章的问题和完成后的行为？
- 每个新概念是否已经在代码或实验中派上用场？
- 每段代码是否有位置、用途和可运行的后续步骤？
- 是否解释了关键状态和控制权，而不只是逐句翻译语法？
- 是否有一个值得亲手观察的正常结果或故障？
- 结论是否来自足够的证据，剩余限制是否交代清楚？
- 读者能否用自己的话说明这一步为什么必要？

## 教程与开发记录

tutorial/v1/ 和 tutorial/v2/ 保存整理后的学习叙述。docs/devlog/ 保存实际开发经过：日期、目标、代码变化、问题、取舍、验证结果和提交。

开发中的试错可以成为教程的材料；选取能解释机制的部分，组织成读者可以复现的实验。完整背景和原始证据通过链接留在开发记录里。

用户已确认[第 04 章](../tutorial/v1/04-agent-loop.md)的叙述与配图风格。后续章节沿用具体任务、观察、解释与实验的推进方式，标题和图的数量按内容需要安排。


## 图怎样参与讲解

图放在读者第一次需要想象数据流、执行顺序或状态变化的位置。先说明图中的对象和场景，再沿着箭头解释代码；图里的文件、调用 ID 和结果尽量与本章实验保持一致。

时序图说明谁调用谁、谁返回结果；流程图说明分支和停止；历史快照图说明数组在不同时间包含哪些项。优先使用可维护的 Mermaid，简单字节边界可以用文本示意，不为每个小节固定配图。

图和代码一样需要核对：箭头是否符合执行顺序，错误分支是否真实存在，省略了哪些字段，展示的是测试安排、预期行为还是实际轨迹。发布前渲染检查中文、换行和布局。

## 阶段与最终实现

章首说明练习起点和该章到达的阶段。使用历史接口时解释它为什么在这一阶段出现，并在收束章节给出当前实现的对应位置；不要把阶段源码描述成最新 v1。

运行命令交代参考仓库和练习目录。模型访问的手动实验、无需密钥的本地测试、独立产物验收各有用途，描述结果时保持清楚的证据边界。开发过程中的行数、测试数量与提交沿革放在开发记录中。
