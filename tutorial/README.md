# 从一个请求开始，长出 CrabLoop

假设我们面前有一个很小的 Rust 项目。它的大部分功能都正常，只有一个测试没有通过：传入空集合时，一个函数给出了错误的结果。

我们想对程序说：“帮我找到这个问题，修好它，再运行一次测试。”

这句话很容易写下来。让它在电脑上变成一次真正的修复，还需要接上几个环节。代码要从文件里读出来；修改要写回磁盘；测试要作为进程运行；测试产生的错误，也要有机会影响下一次修改。

CrabLoop 就从这里开始。我们会先建立一个空的 Cargo 工程，让程序能够发出一条模型请求，并把响应接回来。起初，我们只关心这一次来回：请求中放了什么，响应又带回了什么。

随后，我们会遇到一种新的响应。模型给出的不只是可以显示在终端里的文字，它还可能提出一个动作：读取某个路径下的文件。这个动作此时还只是一份数据。我们需要亲手写一个 Rust 函数，读取文件，再把结果交回去。

等这一步接通，再增加写入和精确修改。之后接入 Bash，让程序有机会运行测试，听见来自真实执行环境的反馈。每多接上一个环节，我们都会停下来运行一下，看看程序究竟多会了什么。

最后，我们把这些动作连成一个循环。测试失败时，错误进入下一次模型请求；模型据此提出新的操作；程序执行，再带回结果。第一版 CrabLoop 的核心，就在这些很具体的来回中长出来了。

到了第二版，我们继续使用这份已经能运行的代码。随着读取和执行的次数增加，历史也越来越长。早先失败的测试要不要保留？刚读取的文件内容有没有必要每次都发送？把旧历史整理成摘要之后，我们又怎样知道关键事实还在？这些问题会带我们走向上下文管理与压缩。

这份教程希望陪你把每一步都写出来，也把每一步为什么存在讲清楚。

## 怎样沿着这条路线学习

v1 围绕模型交互、四个工具和行动循环展开，核心实现目标约 300 行。v2 在相同代码上增加上下文管理与摘要压缩，总目标约 500 行。源码始终位于仓库根目录的 Cargo 工程中。

从[每步完整增量](v1/patches/README.md)准备一个独立练习目录；这条路线已经逐阶段验证，能从空目录一直走到 v1 与 352 行的教学排版副本。每章会给出可以亲手完成的小段修改、运行方法和需要留意的现象。遇到错误时，我们会沿着请求、工具和结果追踪它怎样发生，再决定下一步加什么代码。你可以通过关联的 commit 回看当时的实现，在 v1、v2 tag 上回到完整里程碑。

从 [00 状态地图](v1/00-state-map.md) 开始，再阅读 [01 第一次请求](v1/01-responses.md)、[02 文件工具](v1/02-file-tools.md)、[03 Bash](v1/03-bash.md)、[04 行动循环](v1/04-agent-loop.md) 和 [05 综合任务](v1/05-v1-coding-task.md)。
