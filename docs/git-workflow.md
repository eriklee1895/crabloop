# main 与学习版本怎样一起演进

main 的工作区文件保持最新、已经验证的实现，Git 提交历史保留每轮演进。学习某个旧版本时切到对应分支或标签，不在根目录复制多套 Cargo 工程。

| 引用 | 职责 | 更新方式 |
|---|---|---|
| main | 最新可运行实现、最新教程与路线图 | 每个通过相关检查的小迭代都合入并推送 |
| codex/*（早期也使用 feat/*、fix/*、docs/*） | 正在进行的改动 | 从 main 开始，完成并验证后清理临时分支 |
| milestone/vN | 某版完成时的学习入口 | 完成该版时创建，保持稳定 |
| vN 标签 | 精确的历史验收快照 | 创建后不移动 |
| step-* 标签 | 可运行的中间书签 | 保留细粒度学习节点 |

一次迭代的顺序是：从 main 开始 → 做一个可解释的改动 → 运行与改动有关的检查 → 提交 → 合入 main → 推送 main。没有分叉时使用 fast-forward，直接保留全部小提交；有分叉时正常合并并处理冲突。不要通过 squash 丢掉教学步骤，也不要用 force push 替换历史。

“每轮”指一个可以验收的小增量，不必等 v3 整版完成。尚未能运行的半成品留在开发分支；main 的版本进度在 README/AGENTS 中写明，不把一小步宣称为整个版本完成。

main 的文件内容会逐步从 v2 长到 v3。v1/v2 的内容仍能通过 Git 历史、milestone/v1 与 milestone/v2 分支、v1/v2 标签取回。更新 main 不会覆盖或删除这些书签。

## 当前版本关系

第一版有两个明确入口：原始 `v1` 保存 314 行最小循环；`v1.1` 保存加上使用优化的 571 行交互版。默认工作目录、当前目录 .env、`-p`、输入编辑和多轮会话已经回移到 v1.1。冻结的 v1 和 v2 保留原始命令接口。

Git 中，v1.1 与 v2 都从 v1 演进。主线先走到 v2，随后加入交互；v1.1 是后来为早期学习补出的支线。读者可以按“最小循环 → 交互 → 压缩”阅读，开始下一阶段练习时切到章节指定的基线。不要将 v1.1 的旧 backend 合并覆盖 main。

## 清理临时分支

长期保留 `main`、`milestone/v1`、`milestone/v1.1`、`milestone/v2`，以及全部 `v*` / `step-*` 标签。后续版本沿用相同规则，临时开发分支只在有未完成工作时保留。

清理前先刷新远端引用，确认候选分支 tip 已在 main 历史中；回移分支则确认其提交由已发布的里程碑完整保留。工作树有未提交文件时先处理文件，不直接移除。删除临时分支仅移除名称，已保留的提交仍可从 main 或里程碑访问。

每次清理比较前后的里程碑和标签指向，验证历史快照没有变化。仓库的章节补丁、验收证据和旧提交 SHA 不因分支清理而改写。
