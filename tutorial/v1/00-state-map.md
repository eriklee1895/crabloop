# 00：先看清一次修复是怎样发生的

我们先把注意力放在一个很小的任务上。项目里有一个函数，用来返回集合中最后一个元素的下标。长度为 3，答案应该是 2；集合为空，则没有合法下标。现在它把长度直接当成了下标，测试因此失败了。

我们希望 CrabLoop 能接过这样一句话：“找到这个问题，修好它，再运行测试。”在开始写 Rust 之前，先沿着这句话走一遍，会让后面的代码更容易理解。

## 谁在提出动作，谁在执行

程序首先把任务发给模型。模型可能回答一段解释，也可能提出一个工具调用，例如读取 lib.rs。这份调用包含工具名和参数，仍然只是一份数据。文件还没有被读取。

接下来轮到我们的 Rust 程序。它找到对应的函数，从磁盘读取内容，把结果放进下一次请求。模型看到文件以后，才有机会提出修改或运行测试。一次任务里，这样的来回可能发生很多次。

我们把负责这段过程的程序叫作 harness。它持有历史，执行工具，收集环境反馈，并决定什么时候继续请求、什么时候停止。模型提出下一步动作，harness 则负责把动作变成可观察的执行。

下面是一段**示意交互**，不是本章已经运行出的轨迹：

| 顺序 | 发生什么 | 数据来自哪里 |
|---|---|---|
| 1 | 用户要求修复下标错误 | 用户 |
| 2 | 模型提出 read_file，call_id 为 call_read | 第一次模型响应 |
| 3 | 程序读取文件，回传 call_read 的结果 | 文件系统与 harness |
| 4 | 模型提出 bash，运行已有测试 | 第二次模型响应 |
| 5 | 程序运行测试，回传非零退出码 | 真实子进程 |
| 6 | 模型根据错误提出修改 | 第三次模型响应 |

请先在纸上画出这六步，并尝试接上“修改后再测试”。如果某条消息里说测试失败，沿着箭头追一下：这句话究竟来自模型，还是来自我们刚启动的进程？后面核对结果时，这个区别会反复出现。

## 给这些来回取几个名字

这次用户任务从开始到停止，叫作一个 Run。每请求一次模型，叫作一个 Model turn。一个 turn 可以带回多个 Tool call；每个调用都要有对应的 Tool result。

关联它们的 call_id 很像一个取件号。模型发出 call_read，程序回传的也必须是 call_read。名字相同的工具可以被调用很多次，所以不能只凭 read_file 这个名字判断结果属于哪次调用。

这些概念会逐渐变成 Rust 类型。现在先记住它们分别对应哪个动作；等到代码真的需要区分“工具错误”和“整个运行结束”时，我们再看 enum 和 Result 怎样帮助表达这种区别。

## 从空工程出发

CrabLoop 的 Cargo 工程位于仓库根目录。教程固定 Rust 1.94.0，使用 edition 2024，方便把编译结果对应到同一套工具链。你可以先运行 rustc --version 和 cargo --version，确认环境，再阅读下一章。

根目录已有文档，所以我们直接建立 Cargo.toml 和 src/。你手工重建时，也可以在另一个空目录运行 cargo new crabloop，再把最初的 main.rs 打开。此时程序还只会打印一句话；下一章会把这句问候变成真正的模型请求。

在继续之前，试着回答：模型提出 read_file 时，磁盘已经被读取了吗？一次用户请求为什么可能需要三次模型调用？如果第二次测试没有运行，谁有资格说它已经通过？
