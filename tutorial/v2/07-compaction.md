# 07：先写出候选摘要，再决定要不要使用

上一章只保留最近几组时，旧测试失败的信息会跟着消失。我们希望旧历史更短，同时仍能回答“做过什么、还欠什么”。这就是这次手写摘要的目的。

先看 src/context.rs 的 prepare。每次主请求之前，loop 让它准备 input。小于 soft 时直接返回；达到阈值时，较早完整组作为候选摘要来源，最近两组继续原样保留。没有较早组可移出，或者摘要请求本身超过 hard，就返回 None，由 loop 报告 ContextLimit。

## 摘要是另一次模型请求

这次请求的工作是“整理一份记录”。原任务、项目约定、上一份摘要、较早交互组都放进一个 JSON 对象，作为单独的 user 数据发送，tools 为空。摘要指令要求保留约束、文件、实际测试状态、剩余工作和不确定事项。

为什么要特意包成记录？一次真实实验中，我们最初直接回放了原生工具历史，再在 instructions 中要求总结。DeepSeek 给出了继续读取文件的动作文本。程序因为缺少摘要栏目而拒绝提交，任务停止。把“供总结的数据”与“正在继续的对话”表达清楚，是这次实验教会我们的具体问题；不能只因为请求没有 tools，就假定模型一定理解它的用途。

reasoning 密文仍保存在原记录中，最近两组也保持完整。摘要请求把旧记录当数据，不尝试解释不透明字段。

## 成功返回，还没有提交

模型返回文本后，先检查是否为最终文本、是否偷偷返回工具调用、长度是否超限，以及五类信息的栏目是否齐全。这些检查只描述形状，不证明里面的事实正确。

随后构造一个独立 candidate：原任务不变，新摘要替换旧摘要，最近两组保持原样。重新计算完整请求大小，只有低于 soft 才使用 candidate。实际替换只在最后一处：

```rust
*self = candidate;
```

在这之前发生任何错误，旧工作历史都在。摘要请求的尝试次数会增加，JSONL 也会记录已经发生的请求；我们不会假装一次失败调用从未发生。

运行 `cargo test --locked --test compaction`。测试故意返回空文本、缺栏目、超长文本、incomplete、HTTP 500 和工具调用，确认它们都没有替换历史，更没有执行工具。这比只看一次成功摘要更能解释状态边界。

## 预算里要给谁留位置

v2 的 hard 限制每次请求，soft 提前触发整理，摘要最多 min(4096, hard/8) 字节。摘要请求有自己的大小检查；不能在主请求已经很大时，另发一个更大的总结请求来“解决超限”。

每个主轮前最多整理一次，累计最多 15 次。原任务、工具 schema、项目约定和最近两组本身太大时，即使旧摘要只有一句话，也未必能继续。这个版本会明确停止，让我们看见预算不足的位置。

在准备好的新 fixture 上运行下面的实验，可以观察一次小预算尝试：

```bash
python3 scripts/run-live.py --stage v2 --provider deepseek --context-bytes 8192
```

结果可能是成功压缩，也可能是 ContextLimit；模型合并调用的方式会影响每组大小。下一章会使用较长任务，并对照不压缩的运行。我们要验证的是摘要出现以后还能否完成任务，以及早期事实有没有被改写。
