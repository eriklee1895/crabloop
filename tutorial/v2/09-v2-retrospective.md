# 09：沿着一份记录，重新讲出整个循环

现在的 CrabLoop 仍然是同一个根目录 Cargo 工程。四个工具没有换，模型协议也没有换；增加的是固定上下文、完整交互组、运行记录和一次可以失败的整理过程。

先回到这几个问题：任务由谁保存？一个工具调用在哪里变成真实动作？模型下一轮看到了什么？压缩改变了哪一份状态？如果你能在源码里指出这些位置，就可以离开教程的讲解，自己重建这条路径了。

## 先把循环重写一遍

在仓库之外建立一个练习目录，不看参考 loop，先只写一个函数：接受“发模型请求”和“执行工具”两个操作。第一次请求返回调用，执行后形成结果；第二次请求必须能看到它；最终文本出现时停止。再加轮数上限和明确的停止原因。

先用固定回复验证控制流：第一次返回工具调用，第二次检查关联结果，最后返回文本并停止。

随后把 model::respond 和 tools::execute 接回去，对照第 04 章看看自己漏了哪些东西。尤其检查带多个调用的 output、调用之前的 reasoning、中间 commentary，以及非零退出码怎样继续传给模型。

## 再沿一条真实压缩记录走回来

打开[成功运行的脱敏记录](../../evidence/v2/20261011T143500013361Z-coding-deepseek.json)。完整本地 JSONL 位于该次 workspace 的 .crabloop 中；公开 JSON 保留请求大小、摘要、usage、工具结果摘要和验收。

第一次摘要只覆盖最早一组，所以当时尚未包含后来发生的测试。第三次摘要已经包括基线三项失败和源码修改，却还没有保留修复后的测试；第四次则记录三项实测通过。被保留的最近两组补上最新进度，原任务与 AGENTS 始终留在固定位置。

试着选择一条 compaction：找出 before_bytes、after_bytes 和 removed_rounds，说明被移出的是哪些整组；再在下一个主请求中找到新摘要。JSONL 中那些旧事件仍在，减少的是之后发送的输入。

也读一遍失败记录。摘要 incomplete、候选过大和没有前缀时，程序没有替换旧历史或重试工具。完成能力与停止能力，都属于这个 harness。

## v2 做到这里就够了

[验收表](../../evidence/v2/acceptance.md) 将确定性测试、真实工具执行、真实模型任务与人工复核分开。参考实现约 500 行，没有因此承诺摘要无损、任意模型参数兼容或会话可恢复。

接下来最自然的问题是：每次运行都配置环境，换模型又要查名字，能不能让它记住常用设置？[后续路线](../../docs/roadmap.md) 把这个问题放在 v3：home、TOML、provider 与模型目录。v4 才正式加入 Skills 与网络工具，v5 再研究进程退出后如何继续。

你可以随时切回 milestone/v1 或 milestone/v2 学习分支；v1/v2 标签固定原始验收快照。v1 统一从 milestone/v1 学习，它保留单任务模型—工具循环与简洁启动；完整多轮用户交互在 main。以后 v6/v7 也继续沿用这套版本记录方式。
